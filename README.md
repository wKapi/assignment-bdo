# Assignment-Bdo

bdo-ს შვებულებების MCP სერვერი და ქართულენოვანი CLI ასისტენტი
(RAG პასუხები შიდა პოლიტიკებზე + ბალანსის ნახვა + შვებულების მოთხოვნა).

- **დავალება 1** — MCP სერვერი (stdio) + SQLite ბაზა შვებულებებისთვის.
- **დავალება 2** — Python CLI, რომელიც ქართულად ესაუბრება თანამშრომელს,
  პოლიტიკებზე კითხვებს RAG-ით პასუხობს წყაროს მითითებით, ბალანსს აჩვენებს და
  შვებულების მოთხოვნას ქმნის — ყველაფერი ისევ იმავე MCP სერვერის ხელსაწყოთი.

## მოთხოვნები

- Python 3.11+
- პროექტი `mock` რეჟიმში ეშვება და სრულად მუშაობს: MCP სერვერი, ბაზა, პოლიტიკის
  წესები, მოძიება, ციტირება და ტესტები გასაღებს საერთოდ არ იყენებს.
  `mock` რეჟიმში ასისტენტი კითხვას საკვანძო სიტყვებით ცნობს და პასუხად დოკუმენტების ამონარიდებს აბრუნებს წყაროს
  მითითებით.
- **რეალური LLM-ისთვის საჭიროა ANTHROPIC_API_KEY** (Anthropic Claude API).
  ნაგულისხმევი მოდელია claude-sonnet-5-5, შეიცვლება `.env`-ით.
  გასაღების დამატებისას იცვლება მხოლოდ ერთი რამ: პასუხი
  ამონარიდების ნაცვლად შეჯამებული ტექსტი ხდება.

## გაშვება

```bash
# 1. ვირტუალური გარემო
python3 -m venv .venv
source .venv/bin/activate            
pip install -r requirements.txt

cp .env.example .env        # 2. კონფიგურაცია

# 3. ბაზის შექმნა და CSV-ების ჩატვირთვა
python -m src.db.seed

# 4. RAG
python -m src.rag.index

# 5. CLI ასისტენტი
python -m src.cli.app --employee E1013
```
MCP სერვერის ცალკე გაშვება (stdio, ნებისმიერი MCP კლიენტისთვის):

```bash
python -m src.mcp_server.server
```

**როლები.** `CURRENT_ROLE=employee` — HR ასისტენტის არხი: ხედავს მხოლოდ
საკუთარ მონაცემებს (მუხლი 5.2) და მოთხოვნებს არ ამტკიცებს, არ აუქმებს
 `CURRENT_ROLE=hr` — HR პორტალის არხი.

**ორნაბიჯიანი დადასტურება.** მუხლი 12.2 ითხოვს, რომ შექმნამდე
თანამშრომელს სახე, თარიღები და დღეები ვაჩვენოთ. ამიტომ:
`preview_leave_request` → `proposal_id` → `create_leave_request`.
იმავე `proposal_id`-ით განმეორებითი გამოძახება იმავე`request_id`-ს
აბრუნებს და დუკლიკატს არ ქმნის.

**უარი შეცდომა არ არის.** თუ წესები მოთხოვნას კრძალავს, პასუხში
`created: false` და `violations` სიაა, სადაც თითოეულს აქვს `message`,
`policy_reference` და `redirect_to` (`hr` / `portal` / `manager`).
ToolError მხოლოდ უფლების დარღვევასა და არასწორ არგუმენტზე ბრუნდება.

## მონაცემები და პოლიტიკა

**თარიღების ფორმატი.** `data_dictionary.pdf` ამბობს, რომ CSV-ებში თარიღები
ISO ფორმატშია, თუმცა რეალურად `M/D/YYYY`-ია; ISO 8601 მხოლოდ
`leave_requests.created_at`-ია. seed ორივე ფორმატს იღებს და ბაზაში
ერთგვაროვან ISO ტექსტს წერს.

**„დღევანდელი“ თარიღი.** მონაცემები 2026 წლის 19 ოქტომბრის
მდგომარეობაა, ამიტომ ყველა ვადა `APP_TODAY`-ზე ითვლება (`src/core/clock.py`).
`date.today()` კოდში არსად გამოიძახება.

**ბალანსი.** მუხლი 5.1: `კუთვნილი + გადმოტანილი − დამტკიცებული − განხილვაში`.
`carried_over_days` საწყისი რაოდენობაა და არა ნაშთი (მუხლი 4.7), ამიტომ
ორმაგად არ იქვითება. BEREAVEMENT და PARENTAL წლიურ ბალანსს არ ექვემდებარება;
SICK-ის უარყოფითი შედეგი 0-ია, რაც აღრიცხვას არ კრძალავს (მუხლი 6.4).

**კუთვნილი დღეების წყარო.** `leave_entitlements` ცხრილია ჭეშმარიტების წყარო
(მუხლები 5.1 და 5.3 — ციფრს მხოლოდ HR ასწორებს). შემოწმებულია, რომ სამივე
14 თანამშრომლის `entitled_days` მუხლი 4.1/4.2-ის გამოთვლას ემთხვევა.

**ასისტენტის ფარგლები.** მოთხოვნას ქმნის მხოლოდ ANNUAL, SICK და UNPAID
სახეებზე (მუხლი 12.2). შემოწმებული წესები: 2.1, 2.2, 4.3, 4.4, 4.5, 4.6,
5.1, 6.2, 6.4, 7.1, 7.2 და 12.3 (გადაფარვა, მომდევნო წელი).

## RAG

 დოკუმენტები დანომრილია, ამიტომ საზღვარი სათაურია და
არა ფიქსირებული სიგრძე — ასე ციტირება ზუსტი გამოდის. ორი ნუმერაციაა:
პოლიტიკებში `4.1`, FAQ-ში კი ქართული ასოებით `ა.3`. ნომერი ორნიშნა
ციფრითაა შემოფარგლული, იმიტო რომ სათაურის ბლოკის „2026 წლის 1 იანვრიდან“
მუხლად ჩაითვლებოდა. სულ 261 ნაწილი 7 დოკუმენტიდან.

**PDF-ების გაწმენდა.** ყოველ გვერდზე მეორდება
(`… | ვერსია 3.2 | შიდა გამოყენებისთვის`, `გვერდი N`) — ის იჭრება,
თორემ BM25-ში ყველა ნაწილი ერთნაირად დაემთხვეოდა საერთო სიტყვებს.
DOCX-ის ცხრილები markdown-ად გადადის, რომ მუხლი 4.1-ის სტაჟის ცხრილი
არ დაიკარგოს.

**ქართული ტოკენიზაცია.** რეგისტრი ქართულს არ აქვს, ამიტომ `lower()`
არაფერს ცვლის; რეალური პრობლემა ესაა— „შვებულება“,
„შვებულების“, „შვებულებას“, „შვებულებაზე“ ერთ ფუძემდე მიჰყავს
სუფიქსების მოჭრას. კითხვას დამატებით მცირე სინონიმების
ლექსიკონი ეხმარება („სახლიდან“ → „დისტანციურ“).

წყაროს უპირატესობა ქულას არ ცვლის — თუ FAQ-ს
ხელოვნურად ჩამოვწევთ, მოდელი წინააღმდეგობას ვეღარ დაინახავს. სამაგიეროდ
შედეგებში მინიმუმ 2 ადგილი მოქმედი პოლიტიკისთვისაა დაცული: BM25 მოკლე
ჩანაწერებს ანიჭებს უპირატესობას და გაზომვით კითხვაზე „რამდენი დღე
შემიძლია ვიმუშაო სახლიდან?“ ოთხივე პირველი შედეგი FAQ იყო, მოქმედი
წესი კი კონტექსტში საერთოდ არ ხვდებოდა.

**ასოს აცდენა.** BM25 ზუსტ დამთხვევაზე მუშაობს, ანუ ერთი ასოც
კითხვას აცდენს: „გადამდის მოომდევნო წელზე“ არაფერს აბრუნებდა. ინდექსში
არარსებული ფუძეები `difflib`-ით უახლოეს ვარიანტზე სწორდება (მხოლოდ
4+ სიმბოლოზე, cutoff 0.8).

**ცრუ სათაურები.** ციფრით დაწყებული წინადადება — „5 დღეზე მეტის
გადატანა…“ (მუხლი 4.7-ის ტექსტი) — „მუხლი 5“-ად იწერებოდა და ციტირება
მცდარი გამოდიოდა. ახლა სათაური უნდა იყოს მოკლე, წინადადების
პუნქტუაციის გარეშე და ნუმერაციაში წინ  (1 → 1.1 → 2 → …).
შინაარსის გარეშე დარჩენილი თავის სათაურები შორდება.

**„ვერ მოიძებნა“.** თუ საუკეთესო დამთხვევა 10.0-ზე სუსტია, კონტექსტი
ცარიელია. ზღვარი გაზომილია: 11 რეალურ კითხვაზე ქულა 10.8–29.8,
5 უაზროზე — 3.8–10.6. სრული გამიჯვნა შეუძლებელია, ამიტომ ეს მხოლოდ
პირველი ფილტრია; საბოლოო პასუხისმგებლობა prompt-ს აქვს.

**წინააღმდეგობები.** თითოეულ ფრაგმენტს კონტექსტში ახლავს ციტირება და
წყაროს სტატუსი, ჩანაცვლებულ თავებს კი — მიმთითებელი იმ დოკუმენტზე,
რომელმაც ისინი შეცვალა (სახელმძღვანელოს მე-5 და მე-6 თავი). ასე
პასუხი მოქმედ წყაროს ეყრდნობა და მოძველებულს ცალკე ახსენებს
(შვებულების პოლიტიკა, მუხლი 1.4).

პაკეტში ჩადებული რეალური წინააღმდეგობები:

| საკითხი | მოქმედი წესი | მოძველებული წყარო |
